TASK: Convert UI markdown into a dedicated Docusaurus UI docs section.

SOURCE: inputs/ui/overview.md
TARGET: ui-docs/

This prompt describes how to transform the source UI markdown into a structured multi-page
Docusaurus documentation section under ui-docs/. Follow every step precisely and keep the
process idempotent (safe to rerun).
Apply this process whenever the source markdown or its referenced screenshots are added,
changed, renamed, or removed.

================================================================================
PREREQUISITES (one-time setup — skip if already done)
================================================================================

1. Ensure the separate UI docs plugin instance exists in docusaurus.config.ts:

   Add this plugin entry to `plugins` (or update it if already present):

   [
     '@docusaurus/plugin-content-docs',
     {
       id: 'ui-docs',
       path: 'ui-docs',
       routeBasePath: 'ui',
       sidebarPath: './ui-docs/sidebars.ts',
     },
   ],

   IMPORTANT:
   - Do not change the existing main docs preset config (`docs/`).
   - Do not change the existing api-docs plugin instance.
   - This is a third docs section, isolated like api-docs.

2. Ensure top navigation links to the first generated UI page:

   Add/update one navbar item in docusaurus.config.ts:

   {
     to: '/ui/<first-ui-page-slug>',
     position: 'left',
     label: 'UI Documentation',
   }

   In case of doubt, use `/ui/dashboard`.

   Keep existing navbar items (Documentation, API Reference, etc.) intact.

3. Ensure ui-docs/sidebars.ts exists and exports a valid `SidebarsConfig`:

   import type { SidebarsConfig } from '@docusaurus/plugin-content-docs';

   const sidebars: SidebarsConfig = {
     uiguideSidebar: [{ type: 'autogenerated', dirName: '.' }],
   };

   export default sidebars;

================================================================================
STEP 1 — Discover UI pages and split source markdown one-file-per-page
================================================================================

Read `inputs/ui/overview.md` and discover UI pages dynamically.
Do not assume fixed page names, numbering, or counts.

UI page discovery rules (must satisfy all):
1. Build the page set from BOTH:
   - page-oriented content in the source markdown (especially the screen/page guide section), and
   - referenced PNG filenames.
2. A "UI page" means one clickable element in the UI sidemenu.
3. Group multiple screenshots that belong to the same UI page into that single page doc:
   - Treat numbered variants like `dashboard_0.png`, `dashboard_1.png`, `dashboard_2.png`,
     `dashboard_3.png` as the same UI page (`dashboard`).
   - More generally, strip trailing `_<number>` from PNG basenames when inferring the page key.
4. Do NOT create docs pages for non-page narrative sections (for example workflows/process-only
   sections) unless they map to a real UI page.
5. The generated page count under `ui-docs/` MUST equal the discovered UI page count:
   exactly 1 markdown file per UI page (no splitting one page into many files, no combined
   multi-page docs).
6. In case of doubt, the ordering of pages should be Dashboard, Strategy, Market data, Agent
7. Preserve factual meaning and behavioral accuracy for each UI page section, but rewrite wording
   and structure into natural user-facing prose.
8. Preserve essential technical details even after rewrite:
   - validation rules and required fields,
   - disabled/loading/error/empty states,
   - constraints and expected outcomes.
9. Remove numeric prefixes from generated page titles when helpful for readability
   (for example `2.4 Launch experiment` -> `Launch experiment`), but keep meaning unchanged.

Output layout rules:
- Do NOT generate `ui-docs/intro.mdx`.
- Place discovered UI pages at the root of `ui-docs/` using one slugified filename per page:
  `ui-docs/<ui-page-slug>.mdx`
  (example: Dashboard page -> `ui-docs/dashboard.mdx`).
- Filename rule for pages discovered from screenshots:
  - derive canonical page key from PNG basename after removing trailing `_<number>` when present;
  - then slugify for the target filename.
- If there is content before the first discovered page section, merge a concise overview of that
  content into the beginning of the first generated UI page (do not create a separate intro file).
- Do not keep a monolithic copy of the source markdown under `ui-docs/`.

Rerun/update rules:
- If a target page already exists in `ui-docs/`, overwrite it with newly transformed content.
- Recompute the expected generated UI page set on every run from current source content and
  referenced PNG names.
- Create pages for newly discovered UI pages.
- Update existing generated UI pages.
- Remove generated `ui-docs/*.mdx` pages that no longer map to current UI pages
  (do not keep stale/orphan pages).
- Remove stale `ui-docs/intro.mdx` and stale `ui-docs/sections/*.mdx` files from previous runs.

================================================================================
STEP 2 — Add front matter and version metadata
================================================================================

All generated page output files must be MDX (`.mdx`) with YAML front matter.

Use:

  ---
  title: "<Page Title>"
  sidebar_label: "<Sidebar Label>"
  sidebar_position: <number>
  ---

For generated UI pages:
- Use clear human-readable titles derived from discovered headings.
- Set `sidebar_position` sequentially based on source order, starting at 1.
- Keep `sidebar_label` concise and readable.

Version line:
- Read `inputs/version.txt` if it exists.
- On the first generated page (the one with `sidebar_position: 1`), add a line directly below
  the top heading:

  Version: <value from inputs/version.txt>

- If `inputs/version.txt` does not exist, skip the version line without failing.

================================================================================
STEP 3 — Keep a flat sidebar (no section grouping)
================================================================================

Do not create category metadata for generated pages.

Rules:
- Do NOT create `ui-docs/sections/_category_.json`.
- Keep generated pages at `ui-docs/<slug>.mdx` so the left sidemenu stays flat.
- If `ui-docs/sections/_category_.json` exists from previous runs, remove it.

================================================================================
STEP 4 — Transform markdown links and image references
================================================================================

1. Internal doc links:
   - Remove `.md` extensions in links for Docusaurus doc resolution.
   - Update cross-links to point to generated split-page routes in `ui-docs`.
   - Prefer relative links between generated pages (for example `./<slug>` from another root page).

2. Source path cleanup:
   - Replace repository-internal source paths like `../../specs/...` with valid
     site-friendly paths.

3. Images:
   - Treat all PNGs referenced by the source markdown as source-of-truth screenshots.
   - Parse referenced PNG filenames directly from markdown image links in the source
     (extract basename from each `![...](...)` URL ending in `.png`), then de-duplicate.
   - Do not use repository file globbing as the source of truth for image discovery.
   - PNG discovery rule: every referenced PNG is located in the same directory as the source
     markdown (`inputs/ui/`), even if the markdown link currently uses another path
     (for example `../../specs/ui_docs/images/foo.png`).
   - Resolve each image by basename and copy it from `inputs/ui/<filename>.png` to
     `static/img/ui/<filename>.png`.
   - Existence checks MUST use direct filesystem checks (`test -f`, `ls`, or equivalent),
     not glob results alone, so binary files are not missed by tooling quirks.
   - Update image links in generated docs to `/img/ui/<filename>.png`.
  - Screenshot placement in generated pages:
    - Do not keep a `### Screenshot(s)` (or similar) heading in output.
    - Embed each screenshot next to the paragraph/step that explains that exact UI state
      or action, not as a top-of-page dump.
    - For numbered variants (for example `dashboard_0`, `dashboard_1`, ...), place each
      image in the corresponding walkthrough step in logical reading order.
    - Keep any explanatory sentence concise and action-specific, adjacent to the image.
    - If one screenshot supports multiple nearby points, place it once at the most relevant
      location (do not duplicate).
   - Do not drop screenshot links from generated docs if they were referenced in source.
   - If a referenced PNG cannot be found in `inputs/ui/`, fail the task with a clear error
     listing missing filenames instead of silently removing links.

================================================================================
STEP 4.5 — Rewrite style from spec-like to natural docs
================================================================================

Goal:
Transform page content into practical, human documentation that reads like guidance,
not generated specs.

Rules:
1. Preserve factual meaning and behavior, but rewrite wording and section structure freely.
2. Prefer task flow over rigid templates. Avoid repetitive heading patterns such as:
   - `Purpose`
   - `When to use`
   - `Main actions`
   - `Inputs and validation`
   - `Expected results`
   unless a specific page truly needs them for clarity.
3. Start each generated UI page with a short orientation paragraph that explains:
   - what the page is for,
   - when users typically use it.
4. Organize the body around user actions and sequence:
   - for example: "Start with ...", "Then ...", "If a run fails ..."
5. Keep constraints and edge cases, but weave them into natural prose:
   - required inputs and validation behavior,
   - loading/disabled/error/empty states.
6. Use concise, direct language in second-person voice where appropriate
   (for example, "you can", "use this when").
7. Keep pages skimmable:
   - short sections,
   - bullets only where they improve clarity,
   - avoid long repetitive bullet dumps.
8. Remove repetitive boilerplate and wording artifacts from generated text.

================================================================================
STEP 5 — MD to MDX safety transforms
================================================================================

Apply these markdown-to-Docusaurus quality rules:

1. Ensure JSX-like blocks (Tabs, details/summary) have required blank lines.
2. Convert paired language examples (for example Python/curl) to Docusaurus Tabs when present:

   import Tabs from '@theme/Tabs';
   import TabItem from '@theme/TabItem';

   Add imports once per file and only when tabs are used.

3. Preserve fenced code blocks and tables in valid MDX form.

4. Mermaid is optional:
   - Only apply Mermaid-specific setup if Mermaid diagrams are present in the source.
   - If no Mermaid blocks exist, do not add Mermaid-related config changes.

================================================================================
STEP 6 — Validate build, navigation, and reconciliation
================================================================================

After transformations:

1. Run:

   npm run build

2. Fix any broken links or MDX parsing errors.

3. Verify routes render:
   - all generated page routes under `/ui/<slug>`
   - no route dependency on `/ui/intro`

4. Verify top navbar includes and opens:
   - `UI Documentation` -> `/ui/<first-ui-page-slug>` (or `/ui/dashboard` fallback)

5. Verify screenshot coverage is complete (no PNG is disregarded):
   - Parse all PNG references from the source markdown (by link basename), de-duplicated.
   - Verify each referenced filename exists in `inputs/ui/` using filesystem existence checks
     (`test -f`, `ls`, or equivalent), not glob results alone.
   - Verify each referenced filename exists in `static/img/ui/` after copy.
   - Verify each referenced filename appears in at least one generated `ui-docs/**/*.mdx`
     image link as `/img/ui/<filename>.png`.
   - If any referenced PNG fails any check above, consider the task incomplete and fix it.

6. Verify rerun reconciliation (update mode):
   - Compute expected generated page files from current discovered UI pages using the naming convention
     in STEP 1 (including PNG-name-based page keys).
   - Verify every expected generated page file exists.
   - Verify there are no extra/orphan generated `ui-docs/*.mdx` files outside the expected set.
   - Verify one-to-one mapping: number of generated `ui-docs/*.mdx` files equals number
     of discovered UI pages (exactly 1 markdown per UI page).
   - If stale files exist from previous generations, remove or rename them so the output matches
     the current source exactly.
